
# Agent 状态栏

本地代码总结的状态信息，通过User角色消息发送，配合系统提示词，能减少LLM的调用次数，提高效率。
常用状态栏：
- **时间戳跟踪**
    - 实现：用户消息和工具响应中添加时间戳前缀，如 [2025-09-14 10:30:45]
    - 作用：使 Agent 能够理解时序关系，也为调试和审计提供了信息
- **工具调用计数器**
    - 实现：在工具响应中标注 “Tool call #3 for 'read_file'”
    - 作用：让模型“意识到”自己在某个操作上已经花费了太多次尝试，从而调整策略
- **TODO 列表管理**
    - 实现：每个 TODO 项包含唯一标识符、内容、状态（pending/in_progress/completed/cancelled）和时间戳
    - 作用：外部记忆，工作清单，明确目标
- **详细错误信息**
    - 实现：包含四层内容——错误类型和描述、完整参数的 JSON、调用栈信息，以及针对性的修复建议（如遇到 FileNotFoundError 时建议验证路径、检查工作目录、使用绝对路径）
    - 作用：提高错误的处理效率
- **系统状态感知**
    - 实现：注入当前时间、工作目录、操作系统类型、Shell 环境和 Python 版本等信息。
    - 作用：使 Agent 能够根据环境动态调整任务策略


组合使用效果：
- 时间戳和工具计数器的结合使 Agent 能够理解操作的频率和时间分布
- TODO 列表和系统状态的结合使 Agent 能根据环境调整任务策略
- 详细错误信息和工具计数器的结合使 Agent 在多次失败后不仅能改变策略，还能理解失败的原因



# 用户记忆

## 存储模式
- **Simple Notes**：极简设计。每条记忆是最小的、不可再分的实时。
    - 优点：极低开销
    - 缺点：信息关联性丢失，需要额外操作拼凑出完整信息
- **Enhanced Notes**：增强设计。每条记忆包含完整上下文段落。
    - 优点：保留信息的语义完整，方便检索
    - 缺点：存储冗余（相同信息在多个段落中重复）、更新复杂（属性变化需重写多个段落），以及较长段落不利于后续检索
- **JSON Cards**：采用三层嵌套结构（类别→子类别→键值对，如 personal.contact.email）
    - 优点：更新方便
    - 缺点：当信息设计多方面时，不好归类
- **Advanced JSON Cards**：每个卡片不仅记录事实，还加入信息来源的叙事背景（backstory）、主体身份（person）、与用户的关系（relationship）和时间戳。
    - 优点：解决了消息歧义问题，即一个词在不同句子中指代不同的事物。
    - 缺点：生成和维护成本较高


总结（不同模式之间是 简单性与表达力之间的权衡）：
- Simple Notes 选择了极致简单，牺牲语义完整性
- Enhanced Notes 选择叙事完整性，牺牲结构化和可更新性
- JSON Cards 选择了结构化，牺牲灵活性
- Advanced JSON Cards 选择全面性，牺牲简单性

使用场景：
- Simple Notes 快速记录临时信息；**大量且非关键**的对话事实
- Advanced JSON Cards 处理需要精确消歧和长期维护的关键信息（如用户偏好、关键人物关系）


记忆数据的去重和冲突解决：
    - **触发时机**： 离线的内存维护
    - **去重**： 将规范化内容相同的笔记合并为一条（保留最新更新的）
    - **冲突解决**： 将笔记按第一个标签分组，如果标签组内有不同的内容，则发生冲突，保留最近更新的，删除其他笔记。
