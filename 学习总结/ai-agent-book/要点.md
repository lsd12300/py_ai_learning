## 第二章

### KV Cache

模型每生成一个 token，都要回头看一遍前文所有 token的中间计算结果。如果每轮都从头算一次，当上下文很长时，开销会很大。  
**KV Cache** 会把前文的中间计算结果缓存起来，下一轮只前缀完全不变，就只需要计算新增Token部分。当前缀有变化时，缓存作废，需要从被修改位置重新计算。


三条核心结论：
- **系统提示词和工具定义一旦确定就不要改动。** 任何改动（哪怕只改一个空格）都会导致缓存失效，延迟成倍增加、成本上升。
- **动态信息永远追加到末尾。** 时间戳、用户状态等经常变化的动态信息。
- **使用标准API格式，不自行拼接消息。** 结构化消息会被 Chat Template翻译成模型训练时见过的固定token序列；自行拼接会偏离训练格式，削弱模型的多步思考能力。 对于**缓存**，模型只认token字节序列，只要拼接出的前缀字节级稳定，缓存就会有效。


### 注意力机制

模型每处理一个新词时，需要决定前文中哪些词对理解当前词最重要。  
**注意力机制** 通过三个向量完成找相关词的任务：
- **Query 查询向量**：当前词发出的“搜索请求”。
- **Key 键向量**：每个词的“标签”，用于被搜索匹配。
- **Value 值向量**：每个词的“内容”，匹配成功后被提取。  


具体过程分三步：
1. 生成新词的 Query向量（一串数字，代表“我在找什么”）
2. Query向量与每个词的Key向量进行点积（“匹配度打分”--结果越大越匹配），再归一化（总和为1）得到注意力权重
3. 用这些权重对所有词的Value向量进行加权求和---打分高的词贡献多


**KV Cache底层：**每生成一个新词，它的Query都要与前面所有词的Key做匹配，再用所有词的Value加权求和。如果每次都从头计算所有 K 和 V，计算量会随上下文长度不断增长。通过缓存K和V，让新词直接复用。


**上下文管理错误方式：**
- **动态的系统提示词**：每次提示词都变化，导致KV Cache失效。
- **动态的用户配置**：每次用户配置都变化，导致KV Cache失效。
- **工具定义的动态排序**：每次工具定义都变化，导致KV Cache失效。
- **固定长度的对话历史**： 仅保留最近N条消息（超出时删除最早的消息）。这种方式有**两个问题：**：
  - **KV Cache失效**：删除消息会破坏上下文一致性。
  - **信息丢失**：如果模型在N+M轮对话需要参考被删除的消息，就会产生错误的结果 或者 陷入循环。
- **文本格式化方法**：错误的把结构化的 role-content 消息转换为 “USER: ... ASSISTANT: ...” 这样的纯文本流，偏离了模型训练时使用的标准消息格式。模型需要额外消耗注意力资源来推断角色的边界和对话的结构


### 缓存是架构约束
生产级的 Agent 系统中，缓存不仅仅是性能优化手段，更是架构约束。

**提示词的结构由缓存边界决定。** 系统提示词在物理上被一个缓存边界标记一分为二——标记之前的内容可以跨用户、跨会话进行全局缓存，标记之后的内容则包含用户和会话的特定信息。  
**子 Agent 必须与父 Agent 字节级对齐。** 子 Agent 的提示词、工具定义、模型配置、消息前缀和思考配置必须与父 Agent 的缓存键逐字节匹配。当子 Agent 发起的 API 请求如果前缀与父 Agent 的请求一致，就能命中 API 服务商的 Prompt Cache，从而减少计费和延迟。
**工具结果的替换字符串在首次出现时就被冻结。** 当大型工具输出被替换为摘要预览时，替换后的摘要字符串会被持久化保存。即使后续会话重启，系统也会使用完全相同的替换字符串——以保证恢复后的消息序列与缓存中的字节流一致，避免缓存失效。  


### 提示工程（Prompt Engineering）
提示工程的核心对象是**系统提示词（System Prompt）**。  

#### 语气与风格：系统提示词的“人格”
例如 “You MUST answer concisely with fewer than 4 lines”（你必须简洁地回答，不超过 4 行）。在无法完成任务时要求 “keep your response to 1-2 sentences”（把回复控制在 1-2 句话），并且“不要解释为什么不能做某事”——这种设计避免了 Agent 陷入冗长的自我辩护。大写字母（如 “NEVER do X”）比 “Please avoid doing X” 更能引起模型的“注意”，但过度使用会导致效果被稀释，应保留给真正关键的约束。  

#### 结构化提示：系统提示词的“格式”
现代大语言模型对结构化输入展现出显著的敏感性，这源于训练数据中包含大量的结构化内容。  
XML 标签的使用遵循层次化原则，其标签名称本身就携带语义信息——<working_directory> 能立即告诉模型这是工作目录信息，而纯文本格式“当前目录：/Users/project/src”则需要模型做额外的思考来理解冒号前后的关系。  
Markdown 在保持可读性的同时提供了轻量级的结构，特别适合组织层次化的指令和信息。  
XML 和 Markdown 协同配合，创造了一种双层结构：XML 负责机器可解析的精确语义，Markdown 负责人机共读的组织逻辑。

#### 流程驱动：系统提示词的“组织方式”

```
File Processing Standard Operating Procedure:

Step 1: Validation
   Check if file exists and is accessible
   - If not found → log error and stop
   ↓
Step 2: Classification
   Determine file type based on extension and content
   ↓
Step 3: Preprocessing
   Config files → create backup
   Large files (>1MB) → stream processing
   ↓
Step 4: Execution
   Execute core processing logic based on file type
   ↓
Step 5: Verification
   Ensure integrity of the processed file
```  

这种流程设计让模型在任何时刻都能清楚地知道自己处于哪个阶段、当前步骤的目标是什么、完成后该进入哪个步骤。当遇到异常时，模型可以根据当前所处的阶段确定处理方式，而不是遍历所有规则去寻找匹配项。

#### 业务规则细化：系统提示词的“内容”
模糊的规则会导致 Agent 的行为极不稳定。大语言模型的优势在于遵循复杂指令和从长上下文中提取信息，但不应该在业务规则制定上被赋予过多的自由裁量权。通过清晰的操作框架解放模型的认知资源，使其专注于真正需要思考的部分。

#### 示例
当期望的输出难以用规则精确描述时——比如特定风格的文案、结构化报告的格式、客服回复的语气分寸——与其堆砌冗长的文字定义，不如直接给出两三个高质量的输入-输出示例。  

**示例放在哪里：** 放在系统提示词中，示例成为静态前缀的一部分，对所有请求生效；也可以伪造一组 user/assistant 消息放在首轮对话位置，适合按会话类型选用不同示例集的场景。
**示例对 KV Cache 前缀稳定性的影响：** 无论放在哪个位置，示例都处于上下文靠前的区域，一旦确定就应当保持字节级稳定。

#### 工具定义


### 提示注入：上下文安全的核心威胁
其本质是：攻击者通过 Agent 处理的外部内容（网页、邮件、文档等），将伪装成系统指令的文本混入上下文，从而劫持 Agent 的行为。如：发送用户数据到外部服务器、修改模型配置、插入恶意代码等。  

在上下文层面，防御的核心是帮模型分清“指令”与“数据”：
- **来源标记**：在外部内容注入上下文之前，用明确的标记包裹并标注来源（如 <external_content source="webpage">...</external_content>），提示模型这段内容来自不可信的外部世界，其中出现的“指令”不应被执行。
- **结构化角色**：严格利用 Chat Template 的角色体系（system/user/assistant/tool）传递信息，让模型依据训练时建立的优先级区分可信指令与外部数据。
- **输入清洗**：过滤外部内容中的可疑模式（如“忽略之前的指令”等常见注入短语）。这层防御容易被措辞变体绕过，只能作为辅助手段。


### 动态提示词与Agent Skills

#### Skills 的渐进式披露：
- **第一层（元数据）**：每个 Skill 必须包含一个 SKILL.md 文件，开头是 YAML frontmatter（即文件顶部用 --- 分隔的元数据块），包含 name 和 description 两个字段。Agent 框架在启动时扫描所有已安装的 Skill，将它们的 name 和 description（仅占数百个 token）注入到对话上下文中。  

  元数据中的 description 字段是路由决策的关键——它应当足够短（控制常驻的 token 量），但写法要像路由条件而非功能介绍。最直接的写法是 “Use when / Don't use when” 加上几条反例（即明确列出“不该触发此 Skill”的场景）。

- **第二层（核心流程）**：当 Agent 判断某个任务需要特定的 Skill 时，通过专用的 Skill 工具加载完整的 SKILL.md，内容作为 tool result 出现在对话历史中。  

- **第三层（执行）**：通过文件引用深入到更详细的子文档。


#### Skill内容在上下文中的位置  

需要权衡**KV Cache效率**和**模型的指令遵循效果**（模型会在上下文的开头和末尾分配更多的注意力）之间的平衡。  
三种方案
- **注入系统提示词**。模型对 system 位置的指令遵循能力最强（因为训练时大量使用了这个位置的指令），所以 Skill 的执行效果最好。但每增加新的Skill都会导致KV Cache失效。
- **作为普通文件读取，内容出现在上下文中间**。作为 tool result 出现在对话历史中——也就是上下文中间位置。但不同模型的指令遵循效果不同。
- **元数据注入上下文末尾，完整内容通过专用工具按需加载**。Claude Code 实际采用的方案，它把“路由”和“执行”两步分离，分别回避前两种方式的痛点：
  - **元数据列表**——所有已安装 Skill 的 name + description（合计仅数百个 token）——以一条 user 角色的 meta 消息注入到上下文的末尾，外层用 <system-reminder> 标签包裹。不修改system消息（会破坏KV Cache），又在上下文末尾（指令遵循效果好）。但是采用增量发送策略（首次出现时发送），会随着对话增加会滞留到上下文中间位置，指令遵循效果变差。
  - **完整内容**通过专用Skill工具按需加载，以 tool result出现在对话历史中。


### Agent状态栏
**Agent状态栏** 是Agent框架向模型同步各种动态状态的统一机制，本质是把分散在上下文各处的隐式状态提炼为可直接使用的显式知识。  

注意力机制的一个本质特性：上下文学习更像检索而非推理——模型擅长从已有内容中查找信息，但不擅长主动归纳和总结（每次需要时从已有内容中现算一遍）。  
实际场景：Agent 需要打电话处理业务，系统提示词要求拨打每个商家不超过 3 次。但打了 3 次之后，Agent 经常数不清到底打了几次，又打了第 4 次，甚至陷入循环反复拨打同一个电话。

三条准则：
- **状态栏要用代码维护，别拿大模型去维护。**实际实验发现，用LLM维护状态栏会导致准确率下降。
- **想删掉原始上下文之前，先确认状态栏覆盖了所有会被问到的问题。**
- **把状态栏的准确率当成一线生产指标来盯。** 模型几乎无条件地相信状态栏，既不会去核对，也不会自己重算。

#### Agent 状态栏的构成
**任务规划**：当多步骤任务时，Agent 容易过分关注当前的局部子任务，而忘记用户的原始诉求、核心约束以及后续工作。
**事件的侧信道信息**：为每个事件附加元数据——精确的时间、地理位置、距上次 Agent 回复的时间间隔等。可以帮助模型理解事件的时序关系和环境背景，从而做出更符合情境的决策。
**环境的当前状态**：包括动态的环境信息（系统时间、工作目录等）、异常操作提醒（“该工具已被重复调用 N 次”）、以及从隐式状态到显式状态的转换。
**可用能力清单**：插件化的能力扩展信息（如Skill信息）。

#### 上下文中的位置
作为一条 user 角色的消息插入到上下文末尾，用<agent_status> 标签包裹。既保证了KV Cache约束，又确保了指令遵循效果好。  
内容变动时的更新实现：
- **每轮替换**。每次变动删除旧状态消息，在末尾插入新状态消息。保证上下文中只有一份最新的状态栏，但是KV Cache会失效。
- **持久追加**。不删除旧状态消息，每次变动在末尾插入新状态消息。Claude Code 的 <system-reminder> 采用的就是这种方式。对缓存友好，但是占用token，要提醒模型使用最新的状态栏。
选择经验：**状态更新频繁且轨迹很长时，选择持久追加；轨迹较短或单条状态消息很大（如完整的 TODO 列表加环境快照）时，选择每轮替换。**


### 上下文压缩

压缩上下文的动机：
- **解决长度约束和成本约束**。下文窗口有限，几轮交互就可能撑满窗口，任务被迫中断。同时 token 越多，API 成本越高。
- **提升思考质量**。总结后的知识比原始形式更利于模型使用。而且随着上下文变大，注意力被稀释，模型容易忽略关键信息。

压缩的时机和对象：
- **两次 API 调用之间**
- **System Prompt 和 Tool Definitions 永远不动**。 保证 KV Cache 效率。
- **压缩的对象是对话历史中的 tool results**
- **频率权衡**。不压缩，上下文膨胀到超出窗口限制，任务直接失败；压缩后，虽然损失了部分缓存，但上下文长度可控且信息密度更高。

分层压缩机制（参考 Claude Code 的做法）：
1. **工具结果预算控制：** 大体积的工具输出存到磁盘，模型只看摘要预览。
2. **噪声直接删除：** 低价值的内容（如大量搜索结果中只被使用了几行的内容）直接移除，不做摘要。
3. **API 层微压缩：** 通过API通知服务器压缩上下文，本地不用处理。
4. **归档式摘要：** 逐轮做结构化摘要（像 git log 那样保留每轮的独立记录），保留对话的逻辑脉络。
5. **全量压缩：** 由 LLM 驱动的完整压缩，作为最后手段。  

总结： 前三层实现成本最低、对缓存的扰动可控，应当优先使用；后两层成本较高但压缩效果更强，作为兜底手段。

压缩时的信息保留优先级：
1. **标识符：** 必须原样保留。UUID、hash、IP、端口、URL、文件名等。
2. **架构决策和关键约束：** 不得摘要
3. **已修改的文件列表和关键的变更记录：** 完整保留
4. **验证状态（pass/fail）：** 必须保留
5. **未解决的 TODO 和回滚笔记：** 必须保留
6. **工具输出：** 可以删除，仅保留 pass/fail 结论



## 第三章

### 用户记忆系统

**用户记忆系统：** 一个主动的、持续的学习过程，其目标是构建一个关于用户的简洁而有效的预测模型（如用户的爱好、习惯、价值观等）。

用户记忆能力大致归纳：
- **个人信息保留：** 记住用户身份等长期个人信息
- **偏好追踪：** 跟踪并记住用户的长期偏好
- **上下文切换：** 在多个话题之间切换时保持连贯性
- **记忆更新：** 当用户提供与旧信息矛盾的新信息时能正确处理
- **多会话连续性：** 跨会话保持知识
- **复杂思考：** 基于多个记忆片段联合思考，例如当用户对花生过敏时推荐泰国菜应主动提醒注意花生成分。
- **时间感知：** 记住日期、理解相对时间、进行时间计算。
- **记忆冲突解决：** 识别并处理记忆之间的不一致。

三层评估架构：
1. **基础回忆** —— 这是记忆系统最根本的能力，要求 Agent 能够准确存储和检索用户直接提供的、结构化的、无歧义的信息。
2. **多会话检索** —— 要求 Agent 在面对来自多个不同对象、不同时期的会话时，能检索出所有相关信息并推理判断。
3. **主动服务**—— 要求系统综合跨越多个甚至很久以前的会话信息，提供具有预见性的主动帮助。


用户记忆层次结构：
- **轨迹：** 是单次会话的完整原始记录，按时间顺序追加且不修改。
- **用户长期记忆：** 是跨会话提炼出的稳定信息，会被反复改写、合并、淘汰。
- **业务状态：** 是开发者定义的高层状态抽象，表示任务的逻辑阶段（如“处理请求中”、“等待付款”、“请求完成”）。


用户记忆四种存储格式：
1. **Simple Notes** 每条记忆是一个最小的、不可再分的事实（如 “用户邮箱：john@example.com”）。
   - 优点：开销极低
   - 缺点：信息之间缺乏关联性
2. **Enhanced Notes** 将每条记忆保存为包含完整上下文的段落。
   - 优点：保留信息的叙事结构确保语义完整性和丰富性
   - 缺点：存储冗余（相同信息在多个段落中重复）、更新复杂（属性变化需重写多个段落），以及较长段落不利于后续检索
3. **JSON Cards** 三层嵌套结构（类别→子类别→键值对，如 personal.contact.email、work.position.title），模拟人类分类认知模式。
   - 优点：支持部分更新，可预测且可扩展
   - 缺点：当消息无法分类时，强制归类会丢失多维性
4. **Advanced JSON Cards** 每个卡片不仅记录事实，还加入信息来源的叙事背景（backstory）、主体身份（person）、与用户的关系（relationship）和时间戳。
   - 优点：解决了消歧问题。即 同一条信息在不同场景下不同的含义。 如“张医生”可能是自己的牙科医生，也可能是其他人的心脏科医生。
   - 缺点：生成和维护成本较高


长期记忆的三种分类：
1. **情景记忆：** 关于具体事件和经历的记忆。——记录了一个具体事件的时间、对象和细节。
2. **语义记忆：** 从具体事件中抽象出的一般性知识。——从多次交互中提炼出的稳定特征。
3. **程序记忆：** 关于行为模式和流程的记忆。

总结：
| 分类体系 | 回答的问题 | 具体类别 |
|--------------------------------|-----------|----------------------------------------------------|
| 记忆层次（本章开头） | **存在哪里？** | 轨迹（当前会话）、用户长期记忆（跨会话）、业务状态（任务阶段） |
| 存储格式（“四种存储格式”一节） | **怎么存？** | Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards |
| 认知类型（本节） | **存什么？** | 情景记忆（具体事件）、语义记忆（一般知识）、程序记忆（行为流程） |


记忆压缩策略：
1. **通过重要性评分筛选。** 常见重要性评分思路：
    - **访问频率** 经常被检索的记忆更重要
    - **时间衰减** 越久远的记忆越容易被遗忘
    - **情感强度** 带有强烈情感标记的记忆更易保留
    - **信息独特性** 重复信息的重要性降低
2. **通过聚类实现。** 相似记忆被分组，每组生成代表性摘要。
3. **抽象和泛化。** 从具体情景记忆中提取一般性规律，转化为语义或程序记忆


### RAG 检索增强生成

文档分块策略：
- **固定大小切分：** 按固定的 token 数（如 512）切分，通常在相邻块之间保留一定重叠（如 50-100 token），避免关键句子恰好在边界处被切断。
- **递归/结构感知切分：** 按文档的自然边界（章节标题、段落、句子）递归切分——先尝试按大边界切，块仍超长时再降级到更小的边界。常见格式 Markdown、HTML。
- **语义切分：** 计算相邻句子的嵌入相似度，在语义“断崖”处（相似度骤降的位置）下刀，使每个块内部主题尽量单一。切分质量更高，代价是需要额外的嵌入计算。

**嵌入（Embedding）：** 把每个词或句子转化一个N维向量。
**稠密嵌入** 用深度学习把文本映射到向量空间——语义相近的内容，向量距离也近。使用**余弦相似度** 衡量远近，两向量的余弦值越接近1语义越相似。
**稀疏嵌入** 精确的关键词匹配。它将文档表示为极高维度的向量，绝大多数维度为零，只有与文档中出现的词汇对应的维度具有非零值。

**TF-IDF:** 一个词在文档中出现的频率（TF，词频，Term Frequency）越高，包含这个词的文档数（DF，文档频率，Document Frequency）越少——也就是逆文档频率（IDF，Inverse Document Frequency）越高——这个词就越重要。
**BM25** 引入两个关键参数来修正长文档因词频堆砌而不公平地占优。
   - **k1** 让词频的贡献随着增加而逐渐趋于平缓
   - **b** 控制文档长度归一化，使算法能更公平地处理不同长度的文档

**混合检索** 结合稠密嵌入和稀疏嵌入，以获得更准确的检索结果。
   - 第一阶段 **并行检索**，系统同时向稠密和稀疏两个引擎发送查询。
   - 第二阶段 **结果融合**，负责把两路结果合成一个统一的候选池。
   - 第三阶段 **神经重排序**，对候选池中排名靠前的 N 个候选（如前 50 个）逐一精细打分，产生最终排序。

**Vision Transformer（ViT）** 是一种视觉编码器——将图像分割为固定大小的图像块（Patches），像处理句子中的单词一样将每个块序列化为向量，与文本词向量共存于共享的多模态嵌入空间。

**结构化检索**：索引之前先用 LLM 把知识整理一遍——归纳、抽象、建立关联。
   - 树状层次（RAPTOR），采用自下而上的递归抽象方式。它首先将长文档切分为小的文本块作为“叶子节点”，然后通过聚类算法将语义相近的叶子节点分组。
      - 优点：使检索可以在多个抽象层次上进行，既能精确回答细节问题，也能提供对宏观概念的理解。
   - 实体关系图（GraphRAG），将文档知识建模为由实体（Entities）和关系（Relationships）构成的知识图谱。知识图谱通过实体-关系-实体三元组（Triple）构建信息网络。
      - 优点：
         - **多跳关系推理**。当用户问 “我的医生所在医院的地址” 时，系统需要依次解析 “用户 → 医生 → 医院 → 地址” 这条关系链。
         - **实体消歧**。区分现实世界中两个同名的“张医生”——需要维护关于实体本身的知识。
            - 补充知识： **词义消歧（Word Sense Disambiguation）** 即一词多义，靠上下文感知的嵌入即可解决。 如 bank 有银行和河岸的两个含义。
      - 缺点：语义降级——如“如果下周还下雨，我就取消去海边的计划”——三元组（我，有计划，海滩旅游），会丢失条件逻辑等信息。
      - 实现：先利用LLM从文本中提取关键实体（人物、地点、概念、术语），再提取实体间的各种关系。


适用场景：
   - **混合检索** 能覆盖大多数需求。查询主要是“找到包含某信息的文档片段”
   - **结构化检索** 跨文档综合（如“CPU 的 SSE 指令集和 AVX 指令集在架构上有什么区别”）或多层次导航（如“从整体架构到具体指令的逐步深入”）


## 第四章

OpenClaw 三种内置的自动化机制：
- **Hooks（事件钩子）**：响应 Agent 生命周期中的事件，如会话创建、重置等
- **Cron（定时调度器）**：按 cron 表达式（Unix 系统广泛使用的定时任务语法，如 0 9 * * 5 代表每周五上午 9 点）执行周期性任务，如每周五生成周报、每月初汇总数据
- **Heartbeat（心跳守护进程）**：每隔 N 分钟唤醒一次 Agent，检查是否有需要关注的事项，凭借判断力来避免警报疲劳

**事件触发工具** 是外部事件驱动 Agent 行动的入口。
   - **定时器（set_timer）**处理依赖物理时间的事件。
   - **后台任务监控（monitor_shell）**处理来自异步执行的工具或命令行任务的事件。
   - **外部事件通道（connect_channel）**把新邮件到达、API 回调、IM 消息等外部事件实时推送给 Agent。



## 第五章

**开放任务型通用Agent** = Coding Agent + 文件系统

基础的 Coding Agent 只需配备以下七个核心工具：
   - **Code Interpreter（代码解释器）**：提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码在其中运行即使出错也不会影响宿主机）
   - **Bash Shell（命令行终端）**：在终端中执行命令，如运行测试用例、处理特殊格式文件
   - **读文件工具**：读取代码、配置、文档、日志等
   - **写文件工具**：创建新文件或完全重写现有文件
   - **编辑文件工具**：对现有文件进行局部修改，是代码维护和迭代的核心操作
   - **搜索文件名工具（Glob）**：通过模式匹配快速定位文件系统中的目标文件，例如用 **/*.py 找出项目中所有 Python 文件
   - **搜索文件内容工具（Grep）**：在文件内容中搜索特定的文本模式，例如搜索所有调用了某个函数的代码行

Coding Agent的工程化流程：
   - **项目文档化**。让Agent系统性的理解项目。**项目指令文件**（CLAUDE.md、AGENTS.md等）是业界事实标准——在每次会话开始时被自动注入上下文，相当于项目级的系统提示词。
   - **任务理解与需求澄清**。Agent 需要先搞清楚：具体目标、验收标准等，不在需求模糊的状态下就开始编码。
   - **编写设计文档**。设计文档是将抽象需求转化为具体实现计划的桥梁，应回答核心问题：修改哪些模块及原因，采用什么方案及其相对优势，需引入哪些新依赖，预期对系统的影响。
   - **代码实现与测试**。
   - **文档同步与交付**。如果代码修改涉及架构层面的变化——例如引入新模块、改变模块间依赖关系、修改核心抽象语义——Agent 需相应更新架构文档。


**四层故障**：
   - **API 层**：限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断。这类故障与任务内容无关，是基础设施的噪声。
   - **工具层**：幻觉调用（调用了不存在的工具）、参数畸形（不符合工具的输入约束）、执行抛异常，以及最危险的一种——工具反复返回同一个错误，而模型不加改变地反复重试。
   - **上下文层**：上下文窗口溢出、压缩失败、轨迹结构损坏（如工具调用缺少配对的结果消息）。
   - **控制流层**：死循环（反复执行相同操作却毫无进展）与死亡螺旋（错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应）。
