## 第二章

### KV Cache

模型每生成一个 token，都要回头看一遍前文所有 token的中间计算结果。如果每轮都从头算一次，当上下文很长时，开销会很大。  
**KV Cache** 会把前文的中间计算结果缓存起来，下一轮只前缀完全不变，就只需要计算新增Token部分。当前缀有变化时，缓存作废，需要从被修改位置重新计算。


三条核心结论：
- **系统提示词和工具定义一旦确定就不要改动。** 任何改动（哪怕只改一个空格）都会导致缓存失效，延迟成倍增加、成本上升。
- **动态信息永远追加到末尾。** 时间戳、用户状态等经常变化的动态信息。
- **使用标准API格式，不自行拼接消息。** 结构化消息会被 Chat Template翻译成模型训练时见过的固定token序列；自行拼接会偏离训练格式，削弱模型的多步思考能力。 对于**缓存**，模型只认token字节序列，只要拼接出的前缀字节级稳定，缓存就会有效。


### 注意力机制

模型每处理一个新词时，需要决定前文中哪些词对理解当前词最重要。  
**注意力机制** 通过三个向量完成找相关词的任务：
- **Query 查询向量**：当前词发出的“搜索请求”。
- **Key 键向量**：每个词的“标签”，用于被搜索匹配。
- **Value 值向量**：每个词的“内容”，匹配成功后被提取。  


具体过程分三步：
1. 生成新词的 Query向量（一串数字，代表“我在找什么”）
2. Query向量与每个词的Key向量进行点积（“匹配度打分”--结果越大越匹配），再归一化（总和为1）得到注意力权重
3. 用这些权重对所有词的Value向量进行加权求和---打分高的词贡献多


**KV Cache底层：**每生成一个新词，它的Query都要与前面所有词的Key做匹配，再用所有词的Value加权求和。如果每次都从头计算所有 K 和 V，计算量会随上下文长度不断增长。通过缓存K和V，让新词直接复用。


**上下文管理错误方式：**
- **动态的系统提示词**：每次提示词都变化，导致KV Cache失效。
- **动态的用户配置**：每次用户配置都变化，导致KV Cache失效。
- **工具定义的动态排序**：每次工具定义都变化，导致KV Cache失效。
- **固定长度的对话历史**： 仅保留最近N条消息（超出时删除最早的消息）。这种方式有**两个问题：**：
  - **KV Cache失效**：删除消息会破坏上下文一致性。
  - **信息丢失**：如果模型在N+M轮对话需要参考被删除的消息，就会产生错误的结果 或者 陷入循环。
- **文本格式化方法**：错误的把结构化的 role-content 消息转换为 “USER: ... ASSISTANT: ...” 这样的纯文本流，偏离了模型训练时使用的标准消息格式。模型需要额外消耗注意力资源来推断角色的边界和对话的结构


### 缓存是架构约束
生产级的 Agent 系统中，缓存不仅仅是性能优化手段，更是架构约束。

**提示词的结构由缓存边界决定。** 系统提示词在物理上被一个缓存边界标记一分为二——标记之前的内容可以跨用户、跨会话进行全局缓存，标记之后的内容则包含用户和会话的特定信息。  
**子 Agent 必须与父 Agent 字节级对齐。** 子 Agent 的提示词、工具定义、模型配置、消息前缀和思考配置必须与父 Agent 的缓存键逐字节匹配。当子 Agent 发起的 API 请求如果前缀与父 Agent 的请求一致，就能命中 API 服务商的 Prompt Cache，从而减少计费和延迟。
**工具结果的替换字符串在首次出现时就被冻结。** 当大型工具输出被替换为摘要预览时，替换后的摘要字符串会被持久化保存。即使后续会话重启，系统也会使用完全相同的替换字符串——以保证恢复后的消息序列与缓存中的字节流一致，避免缓存失效。  


### 提示工程（Prompt Engineering）
提示工程的核心对象是**系统提示词（System Prompt）**。  

#### 语气与风格：系统提示词的“人格”
例如 “You MUST answer concisely with fewer than 4 lines”（你必须简洁地回答，不超过 4 行）。在无法完成任务时要求 “keep your response to 1-2 sentences”（把回复控制在 1-2 句话），并且“不要解释为什么不能做某事”——这种设计避免了 Agent 陷入冗长的自我辩护。大写字母（如 “NEVER do X”）比 “Please avoid doing X” 更能引起模型的“注意”，但过度使用会导致效果被稀释，应保留给真正关键的约束。  

#### 结构化提示：系统提示词的“格式”
现代大语言模型对结构化输入展现出显著的敏感性，这源于训练数据中包含大量的结构化内容。  
XML 标签的使用遵循层次化原则，其标签名称本身就携带语义信息——<working_directory> 能立即告诉模型这是工作目录信息，而纯文本格式“当前目录：/Users/project/src”则需要模型做额外的思考来理解冒号前后的关系。  
Markdown 在保持可读性的同时提供了轻量级的结构，特别适合组织层次化的指令和信息。  
XML 和 Markdown 协同配合，创造了一种双层结构：XML 负责机器可解析的精确语义，Markdown 负责人机共读的组织逻辑。

#### 流程驱动：系统提示词的“组织方式”

```
File Processing Standard Operating Procedure:

Step 1: Validation
   Check if file exists and is accessible
   - If not found → log error and stop
   ↓
Step 2: Classification
   Determine file type based on extension and content
   ↓
Step 3: Preprocessing
   Config files → create backup
   Large files (>1MB) → stream processing
   ↓
Step 4: Execution
   Execute core processing logic based on file type
   ↓
Step 5: Verification
   Ensure integrity of the processed file
```  

这种流程设计让模型在任何时刻都能清楚地知道自己处于哪个阶段、当前步骤的目标是什么、完成后该进入哪个步骤。当遇到异常时，模型可以根据当前所处的阶段确定处理方式，而不是遍历所有规则去寻找匹配项。

#### 业务规则细化：系统提示词的“内容”
模糊的规则会导致 Agent 的行为极不稳定。大语言模型的优势在于遵循复杂指令和从长上下文中提取信息，但不应该在业务规则制定上被赋予过多的自由裁量权。通过清晰的操作框架解放模型的认知资源，使其专注于真正需要思考的部分。

#### 示例
当期望的输出难以用规则精确描述时——比如特定风格的文案、结构化报告的格式、客服回复的语气分寸——与其堆砌冗长的文字定义，不如直接给出两三个高质量的输入-输出示例。  

**示例放在哪里：** 放在系统提示词中，示例成为静态前缀的一部分，对所有请求生效；也可以伪造一组 user/assistant 消息放在首轮对话位置，适合按会话类型选用不同示例集的场景。
**示例对 KV Cache 前缀稳定性的影响：** 无论放在哪个位置，示例都处于上下文靠前的区域，一旦确定就应当保持字节级稳定。

#### 工具定义


### 提示注入：上下文安全的核心威胁
其本质是：攻击者通过 Agent 处理的外部内容（网页、邮件、文档等），将伪装成系统指令的文本混入上下文，从而劫持 Agent 的行为。如：发送用户数据到外部服务器、修改模型配置、插入恶意代码等。  

在上下文层面，防御的核心是帮模型分清“指令”与“数据”：
- **来源标记**：在外部内容注入上下文之前，用明确的标记包裹并标注来源（如 <external_content source="webpage">...</external_content>），提示模型这段内容来自不可信的外部世界，其中出现的“指令”不应被执行。
- **结构化角色**：严格利用 Chat Template 的角色体系（system/user/assistant/tool）传递信息，让模型依据训练时建立的优先级区分可信指令与外部数据。
- **输入清洗**：过滤外部内容中的可疑模式（如“忽略之前的指令”等常见注入短语）。这层防御容易被措辞变体绕过，只能作为辅助手段。


### 动态提示词与Agent Skills

#### Skills 的渐进式披露：
- **第一层（元数据）**：每个 Skill 必须包含一个 SKILL.md 文件，开头是 YAML frontmatter（即文件顶部用 --- 分隔的元数据块），包含 name 和 description 两个字段。Agent 框架在启动时扫描所有已安装的 Skill，将它们的 name 和 description（仅占数百个 token）注入到对话上下文中。  

  元数据中的 description 字段是路由决策的关键——它应当足够短（控制常驻的 token 量），但写法要像路由条件而非功能介绍。最直接的写法是 “Use when / Don't use when” 加上几条反例（即明确列出“不该触发此 Skill”的场景）。

- **第二层（核心流程）**：当 Agent 判断某个任务需要特定的 Skill 时，通过专用的 Skill 工具加载完整的 SKILL.md，内容作为 tool result 出现在对话历史中。  

- **第三层（执行）**：通过文件引用深入到更详细的子文档。


#### Skill内容在上下文中的位置  

需要权衡**KV Cache效率**和**模型的指令遵循效果**（模型会在上下文的开头和末尾分配更多的注意力）之间的平衡。  
三种方案
- **注入系统提示词**。模型对 system 位置的指令遵循能力最强（因为训练时大量使用了这个位置的指令），所以 Skill 的执行效果最好。但每增加新的Skill都会导致KV Cache失效。
- **作为普通文件读取，内容出现在上下文中间**。作为 tool result 出现在对话历史中——也就是上下文中间位置。但不同模型的指令遵循效果不同。
- **元数据注入上下文末尾，完整内容通过专用工具按需加载**。Claude Code 实际采用的方案，它把“路由”和“执行”两步分离，分别回避前两种方式的痛点：
  - **元数据列表**——所有已安装 Skill 的 name + description（合计仅数百个 token）——以一条 user 角色的 meta 消息注入到上下文的末尾，外层用 <system-reminder> 标签包裹。不修改system消息（会破坏KV Cache），又在上下文末尾（指令遵循效果好）。但是采用增量发送策略（首次出现时发送），会随着对话增加会滞留到上下文中间位置，指令遵循效果变差。
  - **完整内容**通过专用Skill工具按需加载，以 tool result出现在对话历史中。


### Agent状态栏
**Agent状态栏** 是Agent框架向模型同步各种动态状态的统一机制，本质是把分散在上下文各处的隐式状态提炼为可直接使用的显式知识。  

注意力机制的一个本质特性：上下文学习更像检索而非推理——模型擅长从已有内容中查找信息，但不擅长主动归纳和总结（每次需要时从已有内容中现算一遍）。  
实际场景：Agent 需要打电话处理业务，系统提示词要求拨打每个商家不超过 3 次。但打了 3 次之后，Agent 经常数不清到底打了几次，又打了第 4 次，甚至陷入循环反复拨打同一个电话。

三条准则：
- **状态栏要用代码维护，别拿大模型去维护。**实际实验发现，用LLM维护状态栏会导致准确率下降。
- **想删掉原始上下文之前，先确认状态栏覆盖了所有会被问到的问题。**
- **把状态栏的准确率当成一线生产指标来盯。** 模型几乎无条件地相信状态栏，既不会去核对，也不会自己重算。

#### Agent 状态栏的构成
**任务规划**：当多步骤任务时，Agent 容易过分关注当前的局部子任务，而忘记用户的原始诉求、核心约束以及后续工作。
**事件的侧信道信息**：为每个事件附加元数据——精确的时间、地理位置、距上次 Agent 回复的时间间隔等。可以帮助模型理解事件的时序关系和环境背景，从而做出更符合情境的决策。
**环境的当前状态**：包括动态的环境信息（系统时间、工作目录等）、异常操作提醒（“该工具已被重复调用 N 次”）、以及从隐式状态到显式状态的转换。
**可用能力清单**：插件化的能力扩展信息（如Skill信息）。

#### 上下文中的位置
作为一条 user 角色的消息插入到上下文末尾，用<agent_status> 标签包裹。既保证了KV Cache约束，又确保了指令遵循效果好。  
内容变动时的更新实现：
- **每轮替换**。每次变动删除旧状态消息，在末尾插入新状态消息。
